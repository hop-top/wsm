# WSM Core Concepts

## Overview

WSM (Workspace Session Manager) is an IDE-agnostic workspace history system for developers and AI coding agents. It uses event-sourcing architecture where every message, tool call, and file change is an immutable, replayable record.

## Core Entities

### 1. Workspace

A **workspace** is the top-level container for organizing work. It groups related sessions, events, and snapshots.

| Attribute | Type | Description |
|-----------|------|-------------|
| `id` | ULID | Unique identifier |
| `name` | string | Human-readable name (unique) |
| `status` | enum | `active` or `archived` |
| `description` | string | Optional description |
| `tags` | []string | Optional tags for categorization |
| `metadata` | map | Arbitrary key-value metadata |
| `created_at` | timestamp | Creation time |
| `updated_at` | timestamp | Last modification time |
| `archived_at` | timestamp | When archived (nullable) |

**Lifecycle**: Create → Active → Archive → Unarchive → Delete

### 2. Event

An **event** is an immutable record in the event log. Events are the source of truth for all state changes.

| Attribute | Type | Description |
|-----------|------|-------------|
| `id` | ULID | Unique identifier |
| `workspace_id` | FK | Parent workspace |
| `type` | enum | Event type (see below) |
| `device_id` | FK | Device that produced event |
| `session_id` | FK | Session grouping |
| `agent_id` | FK | Agent that produced event |
| `timestamp` | timestamp | When event occurred |
| `data` | JSON | Type-specific payload |
| `seq_num` | uint64 | Monotonic sequence number |

**Event Types**:
- `workspace.created` / `workspace.updated` / `workspace.archived` / `workspace.unarchived`
- `message.added` - Chat message
- `tool_call.started` / `tool_call.completed` - Tool invocation
- `file.changed` - File modification
- `device.attached` / `device.detached` - Device lifecycle
- `snapshot.taken` - Snapshot creation

### 3. Session

A **session** is a logical grouping of events within a workspace. Sessions can branch and fork.

| Attribute | Type | Description |
|-----------|------|-------------|
| `id` | ULID | Unique identifier |
| `workspace_id` | FK | Parent workspace |
| `name` | string | Session name |
| `parent_id` | FK | Parent session (for branching) |
| `created_at` | timestamp | Creation time |

**Key Behavior**:
- Sessions support forking from any entry point
- Branch trees can be navigated and visualized
- Sessions are stored as JSONL entries

### 4. Device

A **device** represents a physical or virtual machine that produces events.

| Attribute | Type | Description |
|-----------|------|-------------|
| `id` | string | SHA-256 hash of OS/Arch/Hostname |
| `name` | string | Device name |
| `hostname` | string | Machine hostname |
| `os` | string | Operating system |
| `arch` | string | CPU architecture |
| `first_seen` | timestamp | First registration |
| `last_seen` | timestamp | Last activity |

**Key Behavior**:
- Auto-detected from runtime environment
- Deterministic ID based on system fingerprint
- Enables cross-IDE session continuity

### 5. Snapshot

A **snapshot** is a point-in-time materialized view of a workspace.

| Attribute | Type | Description |
|-----------|------|-------------|
| `id` | ULID | Unique identifier |
| `name` | string | Optional name |
| `workspace_id` | FK | Parent workspace |
| `at_seq_num` | uint64 | Sequence number at snapshot time |
| `at_timestamp` | timestamp | When snapshot was taken |
| `message_count` | int | Total messages replayed |
| `tool_calls` | int | Total tool calls replayed |
| `files_changed` | []string | Unique files modified |
| `devices` | []string | Attached devices |
| `sessions` | []string | Active sessions |
| `is_seed` | bool | Whether this is a seed snapshot |
| `generated_at` | timestamp | When snapshot was generated |

**Key Behavior**:
- Generated by replaying events
- Supports incremental updates from last snapshot
- Provides quick workspace state summary

### 6. Agent

An **agent** represents an AI coding assistant or automation tool.

| Context | Examples |
|---------|----------|
| `agent_id` in events | Claude Code, Cursor, Windsurf, Codex, Gemini, etc. |

**Key Behavior**:
- Optional identifier in events
- Enables filtering by AI tool

### 7. Squad

A **squad** is an organized group of autonomous agents designed to work together toward a specific business objective within a workspace. Squads provide structure, interaction contracts, and operational boundaries for multi-agent systems.

| Attribute | Type | Description |
|-----------|------|-------------|
| `id` | ULID | Unique identifier |
| `name` | string | Human-readable squad name |
| `type` | enum | Squad type (see below) |
| `workspace_id` | FK | Parent workspace |
| `agents` | []agent | Agent profiles in this squad |
| `contracts` | []interaction | Interaction contracts with other squads |
| `inherited_from` | string | Global squad template ID (optional) |
| `extends` | string | Parent squad ID (for extension) |
| `created_at` | timestamp | Creation time |
| `updated_at` | timestamp | Last modification time |

**Squad Types** (adapted from Team Topologies):
- `stream-aligned` - Primary value-producing unit, owns pipeline end-to-end
- `enabling` - Temporary capability delivery, has exit condition
- `complicated-subsystem` - Wraps specialized problems behind clean interface
- `platform` - Shared substrate consumed by all other squads
- `orchestrator` - Decomposes goals, routes tasks, synthesizes results
- `sentinel` - Continuous observation and drift detection

**Key Behavior**:
- Squads are designed via squad-topologies skill (produces design artifacts)
- Squad configuration lives in workspace's `squads.yaml`
- Squads can inherit from global squad templates
- Squads can extend other squads (add local customizations)
- Squads can span multiple workspaces (via global agent publishing)

**Agent Lifecycle Operations**:
- **Hire** - Create new agent from scratch (adds to `~/.agents/profiles/` and local squads.yaml)
- **Recruit** - Discover and onboard agent from another workspace (requires publish → link flow)
- **Assign** - Link pre-existing profile to a squad

### 8. Squad Topology

A **squad topology** is the overall structure and organization of squads within a workspace. It defines how squads interact, what interaction modes they use, and how they collectively deliver business value.

| Attribute | Type | Description |
|-----------|------|-------------|
| `workspace_id` | FK | Workspace this topology belongs to |
| `squads` | []squad | All squads in topology |
| `contracts` | []interaction | All interaction contracts between squads |
| `global_templates` | []string | Global squad templates referenced |
| `generated_from` | string | Design artifacts path (squad-topologies skill output) |
| `validated_at` | timestamp | Last validation time |

**Interaction Modes**:
- `x-as-a-service` - Stable, one-way, indefinite (target state)
- `collaboration` - Bidirectional, time-boxed, for unknowns (graduates to x-as-a-service)
- `facilitating` - One-way, time-boxed, enabling squad teaches stream squad
- `supervised-delegation` - Orchestrator delegates but retains oversight

**Design Principles**:
- **Context Load** - Primary constraint: minimize coordination overhead in agent working memory
- **Inverse Conway Maneuver** - Design topology first, let agent communication follow
- **Evolutionary Pressure** - Topologies evolve based on measured interaction patterns
- **Explicit Contracts** - All squad pair interactions have declared modes

**Key Behavior**:
- Topology is generated from squad-topologies skill artifacts
- Validated against interaction mode rules and squad type constraints
- Handed off to workspace operations (TLC) for task execution
- Fully audited via WSM event store (all squad events recorded)

**Lifecycle**: Design → Validate → Configure → Handoff → Evolve

### 9. Format Adapter

A **format adapter** provides IDE session import capability.

| Method | Description |
|--------|-------------|
| `Detect(path)` | Returns confidence score (0.0-1.0) |
| `Parse(path)` | Returns normalized entries |
| `Metadata()` | Returns adapter info |

**Supported Formats**: Claude Code, Cursor, Gemini, Codex, VS Code Copilot, etc.

## Architectural Patterns

### Event Sourcing

```
Commands → Events → State
              ↓
          Snapshots (materialized views)
```

- Events are immutable and append-only
- State is derived by replaying events
- Snapshots optimize replay performance

### Backend Abstraction

The `Backend` interface defines the storage contract:

```go
type Backend interface {
    // Workspace CRUD
    CreateWorkspace, GetWorkspace, ListWorkspaces, UpdateWorkspace, DeleteWorkspace
    
    // Event Log
    AppendEvent, GetEvent, ListEvents, EventCount
    
    // Snapshot Storage
    SaveSnapshot, GetSnapshot, ListSnapshots, DeleteSnapshot
    
    // Device Registry
    SaveDevice, GetDevice, ListDevices, ResolveDevice
}
```

Default implementation: SQLite (`pkg/backend/sqlite`)

### Squad Organization Patterns

```
Workspace Context
      │
      │ Squad-Topologies Skill (design-time)
      ▼
Squad Topology ← squads.yaml (machine-readable config)
      │
      ├──────────────────────────────────────────────────┐
      │                                         │
      ▼                                         ▼
   Squad Formation                        Squad Execution
      │                                         │
      │ • Hire new agents                         │
      │ • Recruit from other workspaces          │
      │ • Assign existing profiles                │
      │                                         │
      ├─────────────────────────────────────────────┤
      │                                         │
      │ Interaction Contracts                      │
      │ (XaaS, Collaboration, Facilitating)      │
      │                                         │
      ├─────────────────────────────────────────────┤
      │                                         │
      │ Handoff to Workspace Ops                │
      ▼                                         ▼
   Task Assignment ← TLC (Task/Workflow System)  → Agent Execution
      │                                         │
      │                                         │
      └─────────────────────────────────────────────┘
                    │
                    ▼
             Audit Trail (WSM Event Store)
             • squad.hired
             • squad.recruited
             • squad.assigned
             • squad.handoff
             • squad.config_changed
```

- Squads organize agents within workspace business context
- Squad-topologies skill generates design artifacts → squads.yaml
- WSM records all squad operations in event store (audit trail)
- Workspace ops (TLC) fetches tasks from handoff → executes via agents
- Topologies evolve based on measured interaction patterns

### Squad Integration Points

**With Workspaces**:
- Squad topology is workspace-scoped (designed FOR specific business context)
- squads.yaml lives alongside workspace.yaml in workspace directory
- Squad events recorded in workspace's WSM event store
- Squads can inherit from global squad templates (shared across workspaces)

**With Sessions**:
- Squad metadata tracks which squad performed which task
- Sessions can be scoped to specific squad operations
- Squad handoff events link to session lifecycle

**With Agents**:
- Agents are profiles managed by APS (`~/.agents/profiles/`)
- Squads reference agent profiles by ID
- Agent capabilities are customized per squad (least permissive principle)
- Agents can be workspace-local or globally available (via publish)

**With APS**:
- `wsm squad hire` creates APS profiles via APS CLI or library API
- `wsm squad recruit` discovers agents in other workspaces' APS profiles
- APS handles agent runtime (capabilities, tools, contexts)
- WSM handles squad orchestration, configuration, and audit

**With TLC** (Task/Workflow System):
- Squad handoff → TLC fetches tasks from backlog/assignments
- TLC executes tasks using squad's agent profiles
- Results recorded back to WSM event store with squad metadata

### Configuration Files

**squads.yaml** - Machine-readable squad configuration (generated from design artifacts):
```yaml
version: "1.0"
inherits_from:
  - global/billing-squad      # Optional: global template references

squads:
  - name: local-billing-ops
    type: stream-aligned
    extends: billing-squad      # Optional: extends another squad
    agents:
      - profile: billing-researcher
        capabilities:
          - web-scrape: true
          - data-extraction: true
      - profile: exo
        capabilities:
          - code-generation: true
          - debugging: true
    contracts:
      - interacts_with: legal-reviewer
        mode: supervised-delegation
        direction: orchestrator → executor
        reclaim_condition: compliance_violation

  - name: local-filer
    type: complicated-subsystem
    agents:
      - profile: document-archiver
        capabilities:
          - document-storage: true
          - indexing: true

agents:  # Workspace-local agent definitions (created via "hire")
  - id: billing-researcher
    capabilities:
      - web-scrape: true
      - data-extraction: true
      - least_permissive: true  # Minimum required capabilities
```

**squad-topologies/ Design Artifacts**:
- `squad-registry.md` - One card per squad with type, purpose, inputs, outputs
- `interaction-contracts.md` - How every squad pair communicates
- `squad-topology.diag` - BlockDiag visualization of full topology
- `design-decisions.md` - What was decided and why
- `next-steps.md` - What to build first

**Resolution Order** (for `squads.yaml`):
1. `<workspace>/squads.yaml` (local workspace)
2. `<parent>/squads.yaml` (parent workspace)
3. `~/.squads/squad-templates.yaml` (global)
4. Stops at $HOME or WSM global directory (whichever comes first)
