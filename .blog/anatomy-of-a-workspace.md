# Anatomy of a Workspace

*Understanding the top-level container for your coding history*

---

A workspace is more than a folder. It's the universe in which your work happens—the container that holds every session, every event, every snapshot, every device that has contributed to a project.

Understanding the anatomy of a workspace is understanding how WSM organizes your professional memory.

---

## What Is a Workspace?

A **workspace** is the top-level container for organizing work. It groups related sessions, events, and snapshots into a single, coherent unit.

Think of it as:

| Analogy | Workspace Equivalent |
|---------|---------------------|
| Git repository | A workspace |
| Project folder | A workspace |
| Codebase | A workspace |

But a workspace contains more than code. It contains the entire history of how that code came to be.

---

## Workspace Attributes

| Attribute | Type | Description |
|-----------|------|-------------|
| `id` | ULID | Unique identifier (sortable by time) |
| `name` | string | Human-readable name (unique) |
| `status` | enum | `active` or `archived` |
| `description` | string | Optional description |
| `tags` | []string | Optional tags for categorization |
| `metadata` | map | Arbitrary key-value pairs |
| `created_at` | timestamp | When the workspace was created |
| `updated_at` | timestamp | Last modification time |
| `archived_at` | timestamp | When archived (nullable) |

### Why ULID?

ULIDs (Universally Unique Lexicographically Sortable Identifiers) have two advantages over UUIDs:

1. **Time-sortable** — You can order workspaces by creation time without a separate query
2. **URL-safe** — No special characters that break paths or queries

## What Lives in a Workspace

```
workspace/
├── Sessions/
│   ├── session-a (main development)
│   ├── session-b (exploration branch)
│   └── session-c (code review)
│
├── Events/
│   ├── workspace.created
│   ├── message.added (1,247 events)
│   ├── tool_call.completed (892 events)
│   ├── file.changed (156 events)
│   └── ...
│
├── Snapshots/
│   ├── snapshot-1 (after MVP)
│   ├── snapshot-2 (before refactor)
│   └── snapshot-3 (current state)
│
└── Devices/
    ├── laptop (macbook-pro.local)
    ├── desktop (dev-machine)
    └── cloud-vm (prod-debug-01)
```

### Sessions

Sessions are logical groupings of events. A workspace can have many sessions—each representing a distinct conversation, debugging session, or task.

### Events

Events are the atomic records. Every message, tool call, and file change is stored as an immutable event. The workspace aggregates all events across all sessions.

### Snapshots

Snapshots are point-in-time materialized views. They're generated by replaying events and provide fast access to workspace state without replaying the entire history.

### Devices

The device registry tracks every machine that has contributed to the workspace. This enables cross-machine continuity and audit trails.

## Workspace Lifecycle

```
Create → Active → Archive → Unarchive → Delete
```

### Create

```bash
wsm workspace create my-project --description "Authentication service"
```

Creates:
- Workspace record with ULID
- Initial `workspace.created` event
- Empty session/event/snapshot collections

### Active

The normal state. Workspaces in active status:
- Accept new sessions
- Record events
- Generate snapshots
- Track devices

### Archive

```bash
wsm workspace archive my-project
```

Archived workspaces:
- Are read-only (no new events)
- Remain queryable
- Can be unarchived
- Don't appear in default listings

Use archival for:
- Completed projects
- Historical reference
- Reducing active workspace clutter

### Unarchive

```bash
wsm workspace unarchive my-project
```

Restores full read/write access.

### Delete

```bash
wsm workspace delete my-project
```

**Warning**: Deletion is permanent. All sessions, events, snapshots, and device records are removed.

## Workspace vs Session vs Event

| Entity | Scope | Contains |
|--------|-------|----------|
| **Workspace** | Project | Sessions, Events, Snapshots, Devices |
| **Session** | Conversation/Task | Events (subset) |
| **Event** | Atomic action | Data payload |

### The Hierarchy

```
Workspace (1)
    │
    ├── Session A (n)
    │       └── Events (m)
    │
    ├── Session B (n)
    │       └── Events (m)
    │
    └── Snapshots (k)
```

One workspace. Many sessions. Many more events. Snapshots cache the state.

## Workspace Reference Resolution

WSM supports flexible workspace references:

| Reference Type | Example | Resolution |
|----------------|---------|------------|
| **Name** | `my-project` | Exact match on name |
| **ID** | `01JX2K3M4N...` | Exact match on ULID |
| **Prefix** | `01JX2K` | Matches ULID prefix |
| **Current** | `.` | Workspace in current directory |
| **Parent** | `..` | Parent workspace (if nested) |

### Example Commands

```bash
# By name
wsm events list my-project

# By ID
wsm events list 01JX2K3M4N5P6Q7R8S9T

# By prefix (auto-completion friendly)
wsm events list 01JX2K

# Current directory's workspace
wsm events list .
```

## Workspace Metadata

Metadata enables custom organization:

```bash
# Set metadata
wsm workspace update my-project --metadata team=backend --metadata priority=high

# Query by metadata
wsm workspace list --filter metadata.team=backend
```

### Common Metadata Uses

| Key | Value | Use Case |
|-----|-------|----------|
| `team` | `backend`, `frontend` | Team ownership |
| `priority` | `high`, `medium`, `low` | Prioritization |
| `status` | `wip`, `review`, `shipped` | Workflow tracking |
| `repository` | URL | Link to code |
| `jira` | Ticket ID | Issue tracking |

---

## Workspace Tags

Tags provide lightweight categorization:

```bash
# Add tags
wsm workspace update my-project --tags auth,security,production

# Filter by tag
wsm workspace list --tags auth
```

### Tags vs Metadata

| Aspect | Tags | Metadata |
|--------|------|----------|
| Structure | Flat list | Key-value pairs |
| Query | `--tags value` | `--filter metadata.key=value` |
| Use case | Categories | Structured data |

## Workspace Isolation

Each workspace is isolated:

| Isolated | Shared (Optional) |
|----------|-------------------|
| Sessions | Device registry (global) |
| Events | Configuration (global) |
| Snapshots | Agent profiles (global) |
| Metadata | |

This means:
- Events in workspace A don't appear in workspace B
- You can have multiple workspaces for the same codebase (different exploration paths)
- Archiving one workspace doesn't affect others

## Workspace Directory Structure

Physical storage layout:

```
~/.wsm/
├── config.yaml                    # Global configuration
├── workspaces.db                  # Workspace index (SQLite)
│
└── workspaces/
    └── 01JX2K3M4N5P6Q7R8S9T/     # Workspace by ID
        ├── workspace.json         # Workspace metadata
        ├── events.db              # Event store (SQLite)
        │
        └── sessions/
            ├── 01JX1J2I3H4G.../
            │   ├── session.json
            │   └── entries.jsonl
            │
            └── 01JX1K2L3M4N.../
                ├── session.json
                └── entries.jsonl
```

### SQLite for Everything

- **workspaces.db** — Global workspace index
- **events.db** — Per-workspace event store

SQLite provides:
- ACID transactions
- Complex queries
- Zero configuration
- Single-file portability

## Cross-Workspace Queries

While workspaces are isolated, you can query across them:

```bash
# All events across all workspaces
wsm events list --all

# All events from specific agent
wsm events list --all --agent claude-3-sonnet

# Search across workspaces
wsm search "authentication" --all
```

### The Global Device Registry

Devices are tracked globally, then referenced per-workspace:

```bash
wsm devices list --global
```

```
DEVICE              OS       FIRST SEEN    WORKSPACES
macbook-pro.local   darwin   Jan 15        my-project, api-service
dev-desktop         linux    Jan 18        my-project
cloud-vm-01         linux    Feb 01        prod-debug
```

## Practical Workspace Patterns

### Pattern 1: One Workspace Per Project

```
~/.wsm/workspaces/
├── auth-service/
├── payment-gateway/
└── admin-dashboard/
```

Simple. Clear. Each project has its own history.

### Pattern 2: One Workspace Per Feature

```
~/.wsm/workspaces/
├── auth-oauth2/          # OAuth2 implementation
├── auth-mfa/             # MFA implementation
└── auth-permissions/     # Permission system
```

Granular. Each feature is independently explorable.

### Pattern 3: One Workspace Per Investigation

```
~/.wsm/workspaces/
├── bug-4512-memory-leak/
├── perf-audit-q4/
└── security-review-auth/
```

Investigation-focused. Each has its own session tree.

## Workspace Commands Reference

```bash
# CRUD
wsm workspace create <name> [--description] [--tags]
wsm workspace list [--status] [--tags] [--filter]
wsm workspace get <ref>
wsm workspace update <ref> [--name] [--description] [--tags] [--metadata]
wsm workspace delete <ref>

# Lifecycle
wsm workspace archive <ref>
wsm workspace unarchive <ref>

# Inspection
wsm workspace inspect <ref> [--events] [--sessions] [--devices]

# Bulk Operations
wsm workspace list --status archived --format json | jq -r '.[].id' | xargs -I {} wsm workspace delete {}
```

## The Workspace as Source of Truth

The workspace is the anchor for everything:

| Question | Answer |
|----------|--------|
| "What projects am I working on?" | List workspaces |
| "What happened in this project?" | Inspect workspace |
| "Who contributed?" | List devices in workspace |
| "What was explored?" | Session tree in workspace |
| "What's the current state?" | Latest snapshot in workspace |

All roads lead back to the workspace. It's the source of truth for your professional memory.

## Summary

| Aspect | What It Means |
|--------|---------------|
| **Container** | Groups all sessions, events, snapshots for a project |
| **Isolation** | Each workspace is independent |
| **Lifecycle** | Create → Active → Archive → Unarchive → Delete |
| **Reference** | By name, ID, prefix, or directory |
| **Metadata** | Custom key-value pairs for organization |
| **Tags** | Lightweight categorization |
| **Storage** | SQLite per workspace, portable single files |

The workspace is where your coding history lives. Understand it, and you understand how WSM organizes your professional memory.
